## Native interaction changes

- Left mouse-down records whether the panel should open or close; mouse-up completes that intent. A blur between them cannot change a close into an open.
- Leaving the status item cancels the press, applies deferred outside-dismiss when appropriate, and consumes a late mouse-up without reopening. The next press starts a fresh action.
- The panel path calls macOS application-wide `unhide` only before any dashboard exists. This preserves background startup while preventing that call from restoring an existing hidden dashboard. With a dashboard present, panel show/focus stays window-scoped; application activation and other-window ordering still need a real native check.
- macOS reopen preserves an actually visible, unminimized dashboard. Otherwise it retries showing the panel, including when the panel itself reports visible but the application is backgrounded. AppKit’s `hasVisibleWindows` counts minimized windows, so it is not used as a screen-visibility signal. Dashboard creation/restoration remains behind explicit menu or panel actions.
- Model regressions cover press/blur/release, cancellation/late release/new press, ordinary and stale blur, and reopen. Independent reviewer findings in the refresh, frontend, and native paths were fixed and re-reviewed; no remaining P1/P2 was found. Reviewer work was read-only by instruction, not OS-enforced sandbox isolation.

## Native UX limits

The macOS status-bar item could not be targeted by computer-use automation: interaction with SystemUIServer timed out. The initial automated inspection reactivated the app and reopened its panel, so that inspection could not establish native focus ordering. A later smoke attempt with unconditional application unhide removed returned `cgWindowNotFound`; startup fallback and minimized-window reopen handling were subsequently corrected and independently reviewed. The final reopen guard was narrowed to preserve only a visible, unminimized dashboard; a panel-only app always retries display. The subsequent isolated smoke check succeeded as recorded below. This does not certify real status-bar click/drag behavior, outside-click timing, app-hidden multi-window ordering, accessibility, or another platform.

## Final macOS smoke check

Computer-use inspection of the final temporary app established:

1. Initial panel appeared with its close, refresh, and dashboard controls.
2. Clicking **Open dashboard** displayed the dashboard.
3. Reacquiring the running app retained the visible dashboard rather than replacing it with the panel.
4. After minimizing the dashboard, automation reactivation displayed the panel.
5. Explicitly clicking **Open dashboard** restored the dashboard.
6. The test app quit successfully after verification.

Automation reactivation is part of these observations; this is not a claim that merely minimizing the dashboard should automatically open the panel. No actual status-item press was injected. Source/model tests, not physical clicks, establish the press/blur/cancel ordering evidence.
